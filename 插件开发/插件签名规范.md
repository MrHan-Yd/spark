# Spark 插件签名规范

> 状态：**三期规范草案 v0.1**（2026-08-25）
> 适用版本：`signature.schema: 1`
> 相关：[插件开发规范.md](./插件开发规范.md) · [插件市场与仓库.md](./插件市场与仓库.md) · [Native插件开发.md](./Native插件开发.md) · [WebView插件开发.md](./WebView插件开发.md)
>
> 本文件是**插件代码签名（code signing）的契约**。Spark 官方签发插件用本文件定义的工具与格式，host 按本文件验签，UI 按本文件展示签名状态。第三方开发者未来签发自己的插件也以本文件为准（v1 仅开放官方签发，第三方签名为后续子阶段）。
>
> 本规范解决一个核心问题：**如何让"官方插件"这个标识不可被第三方伪造**。答案是把"是否官方"的判定建立在签名验证结果上，而不是清单里的自报字段。

---

## 1. 一句话

**Spark 用 Ed25519 私钥对插件目录的内容清单（每个文件的 SHA-256）签名，签名随插件包分发；host 安装/加载时用内置的官方公钥验签，验过即"官方插件"。私钥不在插件里、不在仓库里，第三方无法伪造。**

- 签名签的是**内容**（目录里每个文件的哈希），不是 `.spark-plugin` zip 字节——因为 host 的安装入口是**已解压目录**（`host.plugin.install {path}`），验签必须在 host（可信边界）而非 UI 侧。
- 签名文件 `signature.json` 放在插件包根目录，随 zip 解压一起落盘，host 读它重算哈希验签。
- "官方"判定 = 签名验证通过 **且** 签名 key_id 匹配内置官方公钥。`plugin.json` 不加任何 `official` 字段。

---

## 2. 目标与非目标

### 目标

1. **不可伪造的"官方"标识**：只有持有官方私钥的人能产出"官方插件"标识。
2. **内容完整性**：插件包内任何文件被篡改，签名失效。
3. **防仓库入侵**：即使官方仓库被入侵、插件文件与 `registry.json` 同时被改，签名仍验不过（因为攻击者没有私钥，重签会失败）。这是 sha256 做不到的。
4. **验签在可信侧**：签名验证在 host（Rust）完成，UI 只展示结果，不参与判定。
5. **与现有安装流程无缝**：复用 `host.plugin.install`，不新增 IPC 方法（签名验证是 install 的内部步骤）。

### 非目标（v1）

1. ❌ 三方开发者自助签名与公钥分发（"我信任这个开发者"的公钥导入）。v1 仅验证官方密钥；三方签名为后续子阶段。
2. ❌ 远程吊销列表 / kill switch（需网络与信任锚）。v1 仅本地内置吊销列表，随 host 版本更新。
3. ❌ 签名整个 `.spark-plugin` zip 字节。验签在解压后的目录上进行，不绑 zip 格式。
4. ❌ Windows Authenticode / CA 证书链。host 内置公钥，不需要 PKI/CA 体系。
5. ❌ 二进制级反篡改（防内存补丁）。签名只防磁盘文件被替换，不防运行时注入。

## 3. 密码学选型

| 项 | 选择 | 理由 |
|----|------|------|
| 签名算法 | **Ed25519**（纯实现，ed25519-dalek v2） | 快、签名小（64 字节）、无参数选择余地（避免 RSA/ECC 的参数误用）、纯 Rust 无 C 依赖、审计充分 |
| 哈希 | **SHA-256**（sha2） | 通用、与现有 `registry.json` 的 `sha256` 字段语义一致、Windows BCrypt 也有备用实现 |
| 编码 | base64（standard alphabet） | 签名与公钥的文本友好编码，便于嵌 JSON |
| 随机数（仅签名工具） | `rand` + `rand_core` | 仅 `spark-sign` 生成密钥时用；host 验签不需要 RNG |

> **为何不用 RSA-PSS**：RSA 密钥大、签名大、参数多（hash/MGF/padding/salt 长度），无收益。Ed25519 是现代插件签名的事实选择（VSCode 扩展、Cargo 包虽用 PGP 但同类思路、PyPI 等都在向 Ed25519 迁移）。
>
> **为何不用 Windows BCrypt 原生**：host 已链接 `windows` crate，BCrypt 可做 SHA-256，但 Ed25519 在 BCrypt 的 API 暴露不稳定（不同 Windows 版本差异），引入平台风险。纯 Rust crate 跨版本一致、可测、可在 CI 复现。这是**唯一引入新 Rust 依赖**的地方，见 §14。

## 4. 签名对象与签名格式

### 4.1 签名模型：内容清单签名（content manifest signing）

签名不签 zip 字节，签**插件目录内所有文件的 SHA-256 清单**。原因：

- host 安装入口是已解压目录（`host.plugin.install`），不在 zip 边界验签。
- 内容清单签名在解压后依然有效，可在 install 与 load 两个时机重验。
- 天然支持"单文件被改则整体失效"的细粒度完整性。

### 4.2 签名文件 `signature.json`

放在插件包根目录，与 `plugin.json` 同级。zip 解压后随插件落盘到 `<plugins_dir>/<id>/signature.json`。host 验签时读取此文件。

```json
{
  "schema": 1,
  "plugin_id": "com.spark.translate",
  "version": "0.2.0",
  "algorithm": "ed25519",
  "key_id": "spark-official-v1",
  "signed_at": "2026-08-25T10:00:00Z",
  "files": [
    { "path": "plugin.json",    "sha256": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08" },
    { "path": "index.html",     "sha256": "..." },
    { "path": "assets/style.css","sha256": "..." }
  ],
  "signature": "base64-ed25519-signature-over-canonical-bytes"
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `schema` | number | 是 | 格式版本，当前 `1` |
| `plugin_id` | string | 是 | 必须与 `plugin.json` 的 `id` 一致；不一致拒装 |
| `version` | string | 是 | 必须与 `plugin.json` 的 `version` 一致；不一致拒装 |
| `algorithm` | string | 是 | `"ed25519"`；其他值拒装（前向兼容靠 bump schema） |
| `key_id` | string | 是 | 签名密钥标识，对应 host 内置公钥表中的条目 |
| `signed_at` | string | 否 | ISO 8601 签名时刻，仅记录用，不参与验签 |
| `files` | array | 是 | 被签名的文件清单，见 §4.3 |
| `signature` | string | 是 | base64 Ed25519 签名，覆盖 §4.4 的 canonical bytes |

> **`signature.json` 自身不列入 `files`**（不能签自己）。验签时只对 `files` 列出的文件重算哈希。

### 4.3 `files[]` 规则

| 规则 | 说明 |
|------|------|
| 路径相对插件根，POSIX 风格（`/`），不含前导 `/`、不含 `..`、不含反斜杠 | 与 `插件市场与仓库.md` §9.1 的 Zip Slip 防护语义一致 |
| **签名工具产出前必须规范化路径** | 去 `./` 前缀、折叠 `//`、拒绝绝对路径与 `..`；verify 侧遇到非规范路径直接拒装 |
| 必须覆盖插件目录里**所有文件**（除 `signature.json`），**双向校验** | 遗漏（dir 有文件不在 files[]）或悬空（files[] 列了 dir 没有的文件）均视为不完整，拒装 |
| 路径去重、按 **UTF-8 字节序**排序后参与签名 | canonical bytes 里是排序后的；中文文件名也按字节序，避免两端漂移 |
| 空目录不列（zip 不保留空目录） | 无影响 |
| 不列符号链接（签名只覆盖普通文件） | 与 §9.1 跳过 symlink 一致 |

### 4.4 Canonical bytes（被签名的字节）

签名工具按以下格式拼成 UTF-8 字节串，用 Ed25519 私钥签名：

```
spark-plugin-signature-v1\n
{plugin_id}\n
{version}\n
{algorithm}\n
{key_id}\n
{files: 每行 "{sha256}  {path}"，按 path 字典序，行尾 \n}
```

- 所有 `\n` 为单个 LF，无 BOM。
- `{sha256}` 为 64 位小写十六进制。
- `{path}` 为 `files[]` 里的 POSIX 相对路径原值（已按 §4.3 规范化）。
- 路径按其 **UTF-8 字节序** 排序（非 Unicode 码点序），中文文件名两端一致。
- **host 验签时按完全相同的规则重建 canonical bytes**，再 Ed25519 verify。两端实现共享同一份 canonicalization 函数（见 §9 实现），单测覆盖。
- **验签用的公钥恒来自 host 内置 `TRUSTED_KEYS`**，`signature.json` 里的 `key_id` 仅作索引标识，不被信任为公钥来源——攻击者用自己的密钥签后填 `key_id="spark-official-v1"`，host 查表拿到的是官方公钥，验不过。

### 4.5 与 `registry.json` `sha256` 的关系

| 字段 | 位置 | 作用 | 是否保留 |
|------|------|------|----------|
| `versions[].sha256` | registry.json | 下载 zip 的传输完整性（防下载损坏/中间人） | **保留** |
| `signature.json` | 插件包内 | 内容真实性与完整性（防伪造/篡改） | 新增 |

二者独立：sha256 校的是 zip 字节，签名校的是解压后内容。对官方签名插件，签名已隐含内容完整性，sha256 退化为"廉价预检 + 兜底"；对未签名插件，sha256 是唯一的完整性校验。**不删 sha256**。

### 4.6 registry.json 字段扩展

`versions[]` 新增可选字段 `signature`，承载同一份签名数据（便于市场在下载前就展示"已签名/官方"角标，且作为冗余，防 zip 解压丢 `signature.json`）：

```json
{
  "version": "0.2.0",
  "path": "translate/0.2.0",
  "url": null,
  "sha256": "...",
  "signature": {
    "schema": 1,
    "key_id": "spark-official-v1",
    "algorithm": "ed25519",
    "signature": "base64-..."
  },
  "released": "2026-08-25"
}
```

- `signature` 为 `null` 或缺省 = 该版本未签名（UI 显示"未签名"）。
- 若 `signature` 与包内 `signature.json` 同时存在且不一致，以**包内 `signature.json`** 为准（包内是随包签发的，registry 字段仅作展示与预检）。
- `files` 清单**不进 registry**（体积大且每次版本变），只放 `key_id`/`algorithm`/`signature`，完整 `signature.json` 在包内。
- **预下载徽章非权威**：下载前 UI 用 `registry.signature.key_id` 预判"官方"角标仅供展示；权威判定以 host 装时对包内 `signature.json` 的验签结果为准。即使 registry 被入侵让 UI 误显官方，host 仍会拒装无有效签名的包。

## 5. 密钥模型

### 5.1 内置官方公钥

host 二进制内嵌一张**可信公钥表**，硬编码（不读外部文件、不可被用户修改）：

```rust
// crates/plugin-manager/src/signing/keys.rs
const TRUSTED_KEYS: &[TrustedKey] = &[
    TrustedKey {
        key_id: "spark-official-v1",
        algorithm: "ed25519",
        public_key: "<base64-32-bytes>",  // 仅公钥
        kind: KeyKind::Official,          // 决定 UI 是否显示"官方"角标
        note: "Spark 官方签名密钥 v1",
    },
];
```

- `KeyKind::Official` 的公钥 → 验过即标"官方插件"。
- v1 仅此一条。新增/轮换官方密钥随 host 版本发布（§8）。
- 编译进二进制（`include_str!` 或 `const`），不落盘、不可运行时改。

### 5.2 私钥保管

- 私钥**只在签名机器/CI 上**，绝不进仓库、不进产物。
- 推荐离线介质 / 硬件密钥（如 YubiKey FIDO2/PIV，或本地 HSM）保管；v1 可先用密码加密的密钥文件 + 离线签名机。
- CI 自动签名场景：私钥放 GitHub Actions 加密 secret（或自建 runner），仅在 release 构建时注入；日常开发构建不签。
- 私钥泄露的应急流程见 §8.3。

### 5.3 三方签名（v1 不开放，留接口）

`TrustedKey` 预留 `KeyKind::ThirdParty`，但 v1 `TRUSTED_KEYS` 表只有官方。后续子阶段开放"用户导入第三方公钥"（设置 → 插件 → 受信任开发者），存入 `HostConfig.trusted_pubkeys`，host 验签时合并内置表 + 用户表。本规范不定义其 UI，仅保证 schema 不破。

## 6. 验签时机与策略

### 6.1 策略矩阵

| 场景 | signature.json | 验签动作 | 失败行为 | UI 标识 |
|------|-----------------|----------|----------|---------|
| 市场·官方仓库安装 | 必须有 | host 验签 | **拒装**，提示"官方插件签名校验失败" | "官方" 角标 |
| 市场·自定义仓库安装 | 可选 | 有则验签（仅对官方密钥）；无则跳过 | 官方密钥验失败 → 拒装；三方/无签名 → 警告 | 官方密钥验过="官方"；否则"未签名/三方" |
| 本地导入安装（`host.plugin.install`） | 可选 | 有则验签 | 官方密钥验失败 → 拒装；无签名 → 警告+用户确认后放行 | 同上 |
| 开发目录加载（`host.plugin.devload`） | 不校验 | 跳过 | — | "开发" |
| 启动扫描（`scan_standard`） | 可选重验 | 见 §6.3 | 失败 → 禁用并警告 | "签名失效" |
| 已装的存量插件（升级 host 引入签名前的） | 无 | 视为信任 | 不拦截 | "未签名（存量）" |

### 6.2 install 流程接入点

`install_from_dir`（`crates/plugin-manager/src/lib.rs:301`）在现有"拷贝前读清单 / 拷贝后读清单"之间插入验签步骤，**不新增 IPC 方法**：

```
install_from_dir(src, force, require_signature):
  1. 读 src/plugin.json（已有）
  2. ★ 读 src/signature.json（若有）：
     - 校 schema/plugin_id/version 一致
     - 重算 files 列出文件的 SHA-256
     - 重建 canonical bytes，Ed25519 verify（用内置官方公钥表）
     - 按 §6.1 策略：官方密钥验失败 → Err(PluginError::SignatureInvalid)
     - 无 signature.json → 置 sign_state=Unsigned，由调用方/UI 决定是否放行
  3. 拷贝（已有逻辑，staging + backup swap）
  4. ★ sign_state 写入 LoadedPlugin 与 PluginInfo
```

- `verify_dir` 的返回契约：返回 `Ok(SignState)`；`SignState::Invalid` 表示"有 signature.json 但验签失败"（哈希不匹配/签名不过/格式错），**不作为 Err 抛出**，便于 `list()`/`scan_standard` 把失效状态展示给 UI。
- `PluginError` 新增 `SignatureInvalid(String)` / `SignatureMissing(String)` 变体，由 install 侧据策略决定是否抛：
  - **`Invalid` 一律拒装**（破损签名=可能被篡改，不分 `require_signature`，永不装），install 侧将 `Ok(Invalid)` 转为 `Err(SignatureInvalid)`。
  - `Unsigned` + `require_signature=true` → `Err(SignatureMissing)`。
  - `Unsigned` + `require_signature=false` → 放行，记 `SignState::Unsigned`。
- "来源是否强制签名"由调用方传入：`install_from_dir` 增参 `require_signature: bool`。UI 从市场调用时按 §6.1 设值；本地导入默认 `false`。

### 6.3 启动期重验（可选，分阶段）

`scan_standard` 扫到已签名插件时可重算哈希验签，防"装时真、之后被改"。v1 可先**只校 `signature.json` 存在性 + plugin.json 哈希**（轻量），全量重算放 v1.1。失败处理：禁用插件 + UI 红色提示 + 不影响其他插件加载（与现有"单插件崩溃不影响其他"的隔离原则一致）。

## 7. PluginInfo / IPC / UI

### 7.1 PluginInfo 新增字段

`crates/plugin-manager/src/lib.rs` 的 `PluginInfo` 新增：

```rust
pub sign_state: SignState,

#[derive(Debug, Clone, Copy, Serialize, Deserialize, PartialEq, Eq)]
#[serde(rename_all = "snake_case")]
pub enum SignState {
    Official,    // 签名存在且验过，且 key_id 是官方密钥
    ThirdParty,  // 签名存在且验过，但 key_id 是用户导入的三方密钥（v1 不产生）
    Unsigned,    // 无 signature.json
    Invalid,     // 有 signature.json 但验签失败（仅 scan_standard 重验时出现；install 时已拒）
}
```

- `host.plugin.list` 返回值自动含此字段。
- 不新增 IPC 方法。
- "官方"判定 = `SignState::Official`，由签名验证结果决定，**非清单字段**。

### 7.2 UI 展示规格

| 位置 | 官方 (Official) | 三方 (ThirdParty) | 未签名 (Unsigned) | 失效 (Invalid) |
|------|-----------------|-------------------|------------------|----------------|
| 设置·插件列表 | 名称旁绿色"官方"角标 | 蓝色"已签名"角标 | 无角标 | 红色"签名失效"+禁用开关 |
| 市场·插件卡片 | 标题旁"官方"徽章 | "已签名"徽章 | "未签名"灰色 | — |
| 市场·安装按钮 | 正常 | 正常 | 安装前弹"未签名，确认来源可信" | 禁用 |
| 安装失败提示 | — | — | — | "官方插件签名校验失败，已拒绝安装" |

- native 插件安装时的现有"原生插件拥有完整系统权限"警告（§13.2）与签名状态并存显示，不合并。
- 自定义仓库 + 未签名：叠加显示"第三方仓库" + "未签名"两个提示。

### 7.3 不改清单

`plugin.json` **不加** `official` / `signed` / `vendor` 字段。任何清单字段都可伪造，"官方"只认签名。这是本规范的核心立论。

## 8. 密钥轮换与吊销

### 8.1 轮换（key 版本化）

- 官方密钥带版本号：`spark-official-v1`、`spark-official-v2`……
- 轮换时：新版 host 内置 `v1` + `v2` 两把公钥（overlap），新插件用 `v2` 签，老插件继续用 `v1` 验。overlap 期至少一个大版本周期。
- 私钥不轮换插件签名，老签名一直有效。轮换是为"私钥疑似泄露/定期合规"，不是失效旧插件。

### 8.2 本地吊销列表

host 内置 `REVOKED` 表（编译期，随 host 版本更新）：

```rust
const REVOKED: &[Revocation] = &[
    // Revocation { key_id, plugin_id, version, reason }
    // v1 为空；发现恶意插件后随 host 紧急版本发布
];
```

- 粒度可吊销 `key_id`（整把密钥）或 `(plugin_id, version)`（单版本）。
- 验签时：签名验过但命中吊销 → 视为 `Invalid`，拒装/禁用。
- v1 无远程吊销（需网络 + 信任锚，留 future）。

### 8.3 私钥泄露应急

1. 立即生成 `v2` 密钥对，发布紧急 host 版本（内置 `v2` 公钥 + 把 `v1` 加入 `REVOKED`）。
2. 用 `v2` 重签所有仍在分发的官方插件。
3. 已安装插件不受影响（已验过），但下次启动重验会因 `v1` 吊销而失效 → 需发版提示用户更新插件。
4. 事后审计用 `v1` 签过哪些插件（签名日志，见 §9 工具）。

## 9. 签名工具 `spark-sign`

新增 workspace 成员 `crates/sign-tool`（binary `spark-sign`），独立于 host，只在签名机/CI 跑。

### 9.1 命令

```
spark-sign keygen --out <keyfile> --key-id <id>
    # 生成 Ed25519 密钥对，写 base64 私钥（密码加密）+ 打印公钥

spark-sign sign --dir <plugin_dir> --key <keyfile> --key-id <id>
    # 读插件目录，算每个文件 SHA-256，拼 canonical bytes，签名，
    # 写 <plugin_dir>/signature.json

spark-sign verify --dir <plugin_dir> --pubkey <pubkey_or_builtin>
    # 重算哈希 + 验签；CI/开发者自检用

spark-sign inspect --dir <plugin_dir>
    # 打印 signature.json 内容与验签结果
```

- 私钥文件格式：base64 32 字节 seed，可选 age/密码加密（v1 可先用明文 + 文件权限，文档警告"勿提交"）。
- `sign` 写 `signature.json` 前 dry-run 打印将签的文件清单，避免误签。
- canonicalization 函数抽到 `spark-plugin-manager` 的 `signing` 模块，sign-tool 与 host 共用同一份代码（避免两端不一致）。

### 9.2 签名日志

`spark-sign sign` 追加一行到本地签名日志（不入仓库）：时间、key_id、plugin_id、version、files 数量、签名前缀。供 §8.3 事后审计。

### 9.3 官方插件 CI 签名流程

1. 官方插件源在 `plugins/` 仓库目录（如 `plugins/echo`、`plugins/hello`）。
2. Release 构建：CI 用注入的私钥对每个官方插件目录跑 `spark-sign sign`，产出含 `signature.json` 的目录。
3. 打包成 `.spark-plugin`（zip 根目录直接是插件文件 + `signature.json`）。
4. 上传到官方仓库 `spark-plugins` 的对应版本目录，更新 `registry.json`（含 `versions[].signature`）。

## 10. 开发者签名流程（未来三方）

v1 不开放，记录后续形态：

1. 开发者 `spark-sign keygen` 自备密钥对。
2. `spark-sign sign` 签自己的插件。
3. 用户在设置 → 插件 → 受信任开发者，导入开发者公钥（base64），存入 `HostConfig.trusted_pubkeys`。
4. host 验签时合并内置官方表 + 用户导入表；验过即 `ThirdParty`，UI 蓝角标。
5. 公钥分发不强制走仓库，由开发者自行公示（README / 主页），用户自负信任。

本规范 v1 的 schema 与 canonicalization 对此已前向兼容，无需改 `signature.json` 格式。

## 12. 回滚与迁移

1. **host 引入签名前的存量插件**：升级后首次启动，已装插件无 `signature.json` → `SignState::Unsigned`，**不拦截、不禁用**，UI 标"未签名（存量）"。用户可手动重装官方签名版。
2. **官方仓库分阶段强制**：
   - 3.0：验签能力上线，官方插件全部签名，市场显示角标；旧未签名官方插件仍可装（警告）。
   - 3.1：官方仓库新版本必须签名，未签名版本拒登入 `registry.json`（仓库准入规则，非 host 强制）。
   - 3.2：host 可选"严格模式"开关（仅装官方签名插件），默认关。
3. **签名验证 bug 紧急回滚**：验签逻辑独立模块（`signing`），可加 feature flag `plugin-signing-verify` 在 hotfix 构建临时关闭，避免阻塞性问题。但默认必须开。

## 13. 依赖与构建影响

### 13.1 新增 Rust 依赖

| crate | 用途 | 用在哪 | 纯 Rust |
|-------|------|--------|---------|
| `ed25519-dalek` (v2) | Ed25519 sign/verify | `plugin-manager`（verify）+ `sign-tool`（sign/verify） | ✅ |
| `sha2` | SHA-256 文件哈希 | `plugin-manager` + `sign-tool` | ✅ |
| `base64` | 签名/公钥编解码 | 同上 | ✅ |
| `rand` + `rand_core` | 仅 keygen 生成密钥 | `sign-tool` only | ✅ |

- 这是**本规范对"零新 Rust 依赖"原则的明确例外**——该原则（`marketplace-spec-done` memory）原本约束的是**二期 UI 驱动的市场功能**（UI 用 .NET HttpClient/ZipArchive，host 不加 HTTP/zip）。签名是三期新能力，密码学无可回避。
- 全部纯 Rust、无 C 依赖、跨平台一致、可在 CI 复现，与离线构建兼容（首次需联网拉取，拉取后可 vendor）。
- 不在 `crates/sdk`、`crates/ipc`、`crates/index` 引入任何新依赖（保持 SDK 精简）。

### 13.2 不新增 IPC 方法

签名校验是 `host.plugin.install` / `scan_standard` 的内部步骤。`PluginInfo.sign_state` 随 `host.plugin.list` 自然返回。无新 IPC 方法、无新 `HostMethod` 枚举值。

## 15. 未决问题（待实现时定）

1. **私钥首版保管方式**：加密文件 + 离线机 vs 直接 GitHub Actions secret。倾向前者（更安全），但 CI 自动签名便利性 vs 安全性的取舍留给实施。
2. **canonicalization 的 host/tool 共享**：放 `spark-plugin-manager::signing` 公共模块，还是单独 `crates/signing` 被 `plugin-manager` + `sign-tool` 共依赖。倾向前者（少一个 crate）。
3. **`signature.json` 是否进 `plugins-state.json` 缓存**：避免每次 scan 重算。倾向不缓存（重算廉价、防缓存与磁盘不一致）。
4. **严格模式默认值**：3.2 引入时默认关，还是默认开（破坏存量）。倾向默认关 + 用户主动开。
5. **native 插件 exe 本身**：exe 作为普通文件进 `files[]` 哈希即可，无需额外 Authenticode。是否叠加 Authenticode 留 3.3 评估。
