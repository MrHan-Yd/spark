# 插件签名体系：威胁评审与整改清单

> 版本：v0.1 · 日期：2026-08-28
> 范围：对《插件签名规范.md》（三期 v0.1 草案）及配套 host 实现的安全评审。
> 结论前提：**官方私钥未泄露**。本文回答的问题是——私钥安全的前提下，「官方签名/官方标识」还存在哪些绕过路径、各自怎么整改。
> 定位：本文不修改签名格式的任何契约，只列实现与落地层面的漏洞与整改项。

---

## 0. 结论摘要

- **签名数学层不可仿冒**：Ed25519 + host 内置公钥 + 内容清单签名，在私钥不泄露的前提下，无法伪造「改动后内容 + 有效官方签名」的组合（见 §1）。
- **真实风险全部在四类结构性问题上**：时间窗（验过之后被改）、集合差（验的和跑的不是同一批文件）、入口旁路（存在不验签的安装路径）、信任根（host 本体被替换）。
- 整改优先级：**P0 = V1（装后篡改/启动期重验）+ V2（验签集合=加载集合）+ V3（安装入口收敛）**。这三项落地之前，「官方」标识不构成对内容未被篡改的持续承诺。

| 编号 | 威胁 | 优先级 | 状态 |
|------|------|--------|------|
| V1 | 装后篡改（TOCTOU） | P0 | 规范路线图 3.2 已规划，建议提期 |
| V2 | 验签集合 ≠ 加载集合（symlink/重复条目/穿越/多余文件） | P0 | 规范有条款，实现必须较真 |
| V3 | 安装入口未收敛 / 紧急开关可触达 | P0 | 需实现约束 |
| V4 | registry 签名字段被当权威 | P1 | 规范 §5 已定红线，实现别破 |
| V5 | 信任根：host 本体与更新链 | P1 | 需专项保障 |
| V6 | 旧版本回放/重放 | P2 | 依赖 §8.2 吊销列表落地 |
| V7 | 插件间横向篡改 | P2 | 需隔离 |
| V8 | 用户覆盖 = 人肉绕过 | P2 | 设计纪律 |
| V9 | 官方标 ≠ 安全保证 | P2 | 认知与权限最小化 |

## 1. 已确认不可行的攻击（无需整改，列出以正视听）

以下路径在私钥不泄露的前提下均不成立，整改时不要在这些方向浪费精力：

| 攻击路径 | 为什么不行 |
|------|------|
| 直接伪造 `signature` 字符串 | 等价于从 Ed25519 签名反推私钥，计算不可行 |
| 改一个字节后重用原签名 | 签的是内容清单（每文件 SHA-256），改一个字节即验签失败 |
| 自带密钥签名、冒填 `key_id="spark-official-v1"` | 公钥恒从 host 内置 `TRUSTED_KEYS` 查表（规范 §4.4），key_id 仅是索引不是公钥来源 |
| 把别家正版插件的 `signature.json` 拷进自己的包 | `files[]` 哈希与本包文件对不上；`plugin_id`/`version` 参与签名，跨包移植失败 |
| 连 GitHub 仓库一起入侵，改文件+改 registry | 重签需要私钥（规范 §2 目标 3），这正是签名相对裸 sha256 的价值 |
| SHA-256 碰撞 / Ed25519 签名伪造 | 不在现实威胁模型内 |

**前提性风险**：以上全部成立的前提是私钥安全。私钥保管纪律见 §3。

## 2. 漏洞与缺口清单

### V1 装后篡改（TOCTOU）——当前架构最现实的一条 【P0】

**漏洞**：验签只发生在安装时。装完之后插件目录（用户 profile 下）对所有用户级进程可写。攻击者直接编辑 `index.html`，无需伪造任何东西——徽章是安装那一刻发的，之后无人回头看。`signature.json` 同目录同样可写，可被一起删改。

**攻击链**：恶意程序获得用户级执行 → 修改已装插件文件 → host 下次启动照常加载被改代码，且顶着官方角标。

**影响**：官方标识被用作恶意软件的**驻留通道**（每次 host 启动自动加载、重启存活、外观可信）与**信任伪装**（继承用户对官方插件的授权与信任印象）。

**定位要诚实**：能改用户电脑文件的程序已有代码执行能力，本攻击不是入侵第一步，而是「让官方标识体系变成恶意软件的伪装载体」。

**整改**：
1. host 启动时对全部已装插件**重验**（= 路线图 3.2 的「启动期全量重验」，建议从 3.2 提期到当前阶段）；
2. 插件入口页每次加载前重验该插件（覆盖 host 长时间运行期间被篡改的情况）；
3. 失败处置：摘官方标 + 拒载 + 明确提示「插件已被篡改」（把静默绕过变成可见事件）；
4. **缓存的一切验签结果（含「曾经验过」状态）永不作为依据**——公钥在二进制里，官方与否每次从磁盘 + 内置公钥现场判定。攻击者无论怎么摆弄可写文件，都拼不出「改动后内容 + 有效官方签名」。

### V2 验签集合 ≠ 加载集合 【P0】

**漏洞**：验签器检查的文件集合与 host 运行时实际加载的文件集合只要错开一个文件，签名即被架空：

- **symlink**：规范 §4.3 规定签名只覆盖普通文件、不列符号链接——若加载器不拒绝 symlink，`index.html` 本身可以是指向目录外恶意文件的软链（不在验签集合、在加载集合）；
- **zip 同名重复条目**：解压器与验签器取条目策略不一致（如一个取最后一个、一个取第一个），验的是白文件、跑的是黑文件；
- **路径穿越（zip-slip）**：条目名带 `../`/绝对路径，解压到插件目录之外（规范 §4.3 已定路径规范化，解压器必须执行）；
- **多余文件**：目录里存在 `files[]` 未列出的文件。只验「列出的都匹配」不够，必须同时拒「列了不存在的」和「存在未列的」（§4.3 双向校验）。

**整改原则（一句话）**：**host 运行时读的每一个文件，必须就是验过哈希的那一个文件。**
落地：解压/加载边界统一执行——拒 symlink、拒重复条目、拒非规范路径、双向校验文件集合；加载器读的文件必须 ⊆ 验签通过的集合。

### V3 安装入口未收敛 【P0】

**漏洞**：市场下载只是入口之一。只要存在任何一条不走验签的安装路径，攻击者就走那扇门。需要盘点的入口：

- 市场下载安装（主路径，规范已覆盖）；
- 本地目录安装 / 拖拽安装；
- 开发模式加载（存在即合理，但必须保证：终端用户侧默认不可达、有响亮标识、不参与官方角标判定）；
- **`host.plugin.install {path}` 插件 API**——已安装（哪怕真官方）插件若能经此安装其他内容而验签标准有出入，官方插件就成了绕过的跳板；
- **§12 紧急回滚 feature flag（`plugin-signing-verify`）**：它本身就是一个给绕过留的开关。若能被配置文件/环境变量/命令行打开，攻击者哄骗用户改个设置即可，连插件都不用改。

**整改**：
1. 所有安装入口收敛到**同一个 verify 函数**（代码级收敛，禁止各入口自行实现简化版验签）；
2. feature flag：默认编译进二进制且开启，用户侧不可触达，仅 hotfix 构建可临时关闭（§12 原意），并在关闭期间 UI 全局警示；
3. 开发模式在终端用户构建中默认禁用或强提示。

### V4 registry 签名字段被当权威 【P1】

**漏洞**：`registry.json` 里的 `versions[].signature` 对象就是仓库里一份数据，任何能改仓库（或未来任何分发渠道）的人都能把别家的签名对象复制粘贴到自己条目上，骗取 UI 预显「官方」角标。

**规范已有红线（§5）**：预下载徽章非权威；权威判定 = 安装时对包内 `signature.json` 的验签。

**整改（实现纪律）**：安装判定、角标授予的代码路径**只**允许依赖「包内 signature.json + 内置公钥」的验签结果；registry 字段仅用于下载前的展示，且安装后必须被真实验签结果覆盖。任何 UI 状态不得在无包内验签的情况下标官方。

### V5 信任根：host 本体与更新链 【P1】

**漏洞**：`TRUSTED_KEYS` 硬编码在 host 二进制（§5.1）——设计正确，但这意味着**信任根是 host 本体**。攻击者不发假插件，发一个内置自己公钥的「假 host」或一个被改过的更新包，之后给自己的代码签名，全部验签通过、官方标全亮。

**整改**：
1. host 自身更新包必须签名校验 + HTTPS + **防降级**（拒绝安装比当前更旧的版本，防「合法签名但带漏洞的旧 host」重放）；
2. 签名功能上线前的旧版 host 对签名体系完全无感，属于无保护存量——评估「最低 host 版本」策略或升级引导；
3. host 二进制分发渠道（官网/更新服务器）纳入与私钥同等等级的保管清单。

### V6 旧版本回放 / 重放 【P2】

**漏洞**：旧版本的合法签名永远有效。攻击者伪造不了新版，但可以把**有漏洞的旧签名版本**持续分发，签名照验通过。

**整改**：规范 §8.2 的本地吊销列表（可吊销 `key_id` 或 `(plugin_id, version)`）+ 启动期重验落地后才闭环（依赖 V1 的重验基建）。发现某版本有漏洞 → 加入吊销列表 → 随 host 版本分发。

### V7 插件间横向篡改 【P2】

**漏洞**：无文件隔离时，插件 A（哪怕是真官方签名）可以写插件 B 的目录——变相实现 V1 的装后篡改，且无需任何外部恶意程序。

**整改**：插件目录写隔离（至少：插件运行时禁止写入 `<plugins_dir>` 下其他插件的目录）；与权限系统联动，写其他插件目录需要显式权限。

### V8 用户覆盖 = 人肉绕过 【P2】

**漏洞**：每一个「仍要安装」「忽略警告」按钮都等于给攻击者配一把不用偷的钥匙。规范 §6.1 对存量未签名插件「不拦截、标未签名（存量）」是合理兼容决策，但要警惕未来为安装率添加宽松的覆盖路径。

**整改**：覆盖类操作要求响亮确认 + 说明后果；官方角标永远不可被用户操作手动授予。

### V9 官方标 ≠ 安全保证 【P2】

**漏洞**：签名只证明「这些字节是官方发过的」，不证明「插件无危害」。一个正经签名的插件若权限过宽或自身有漏洞，攻击者利用的是它的能力与身份，不是签名缺陷。

**整改**：权限最小化（逐插件声明最小权限集）；插件能力沙箱与签名体系是两层独立的防线，都不可省。

## 3. 私钥保管纪律（一切结论的前提）

- `spark-sign` 私钥**离线保存**；不进仓库、不进聊天记录、不进网盘/同步盘、不上构建机；
- 记录密钥使用与签发日志（何时、何插件、何版本）；
- 泄露应急：按 §8 走 `key_id` 轮换 + 吊销列表——建议**现在就演练一次**轮换流程，别等出事才第一次跑；
- 公钥、签名值本身是公开数据（贴在聊天/issue 里无所谓），只有私钥是秘密。

## 4. 验收：篡改测试矩阵（整改完成后逐项过）

| # | 用例 | 期望 |
|---|------|------|
| 1 | 安装后修改 `index.html`，重启 host | 启动重验失败：摘标 + 拒载 + 提示已篡改 |
| 2 | 安装后修改 `signature.json` 的 `files` 清单 | 验签失败（canonical bytes 变化） |
| 3 | 安装后删除 `signature.json` | 判定非官方，拒载 |
| 4 | 用其他正版插件的 `signature.json` 覆盖 | 验签失败（文件哈希/字段不匹配） |
| 5 | 包内 `index.html` 为符号链接 | 拒装 |
| 6 | zip 含同名重复条目 | 拒装 |
| 7 | zip 条目含 `../` / 绝对路径 | 拒装 |
| 8 | 目录中存在 `files[]` 未列出的文件 | 拒装（双向校验） |
| 9 | 自签密钥 + 冒填 `key_id="spark-official-v1"` | 验不过（公钥查表非攻击者公钥） |
| 10 | registry 抄别家 signature 对象 | UI 预显可能误亮，**装时必须拒** |
| 11 | 已吊销版本的合法签名包 | Invalid，拒装 |
| 12 | 经 `host.plugin.install` API 安装未签名包 | 与市场安装同标准拒装 |
| 13 | feature flag 尝试从用户侧关闭验签 | 不可达；开启中时 UI 有全局警示 |
| 14 | 官方插件 A 尝试写插件 B 目录 | 被隔离/拒绝 |

## 5. 整改顺序建议

1. **P0 三项先行**：V1 启动期重验（验签函数已存在，成本 = 再调一次，收益 = 关掉最现实的攻击窗）、V2 边界校验（解压/加载统一策略）、V3 入口收敛。
2. **P1 跟进**：V4 实现纪律（写进 code review 清单即可）、V5 host 更新链专项。
3. **P2 排期**：V6 依赖吊销列表落地；V7/V8/V9 属于持续设计纪律。
4. 每项整改以 §4 测试矩阵对应行作为验收标准。
